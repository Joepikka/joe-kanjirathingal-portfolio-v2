Study note 01 · Python & full stack

One request.
Several responsibilities.

My current training ↗

I'm currently taking six-month Python Full-Stack Development training at SMEClabs, Kochi, alongside my B.Tech in Artificial Intelligence.

A useful way to study a web application is to follow one request: the browser collects input, the server checks it, a data layer stores or retrieves it, and the response updates the interface. Each boundary needs a clear contract.

A small Python example

This illustrative function checks a quantity before a request reaches persistence. It is a teaching example, not code extracted from a project.

def checked_quantity(value: int) -> int:
    if isinstance(value, bool) or not isinstance(value, int):
        raise TypeError("Quantity must be an integer")
    if value < 1:
        raise ValueError("Quantity must be positive")
    return value

Frontend feedback improves usability; the server still needs to enforce the rule. A database constraint can protect the same invariant when other code writes data.

Study note 02 · Model evaluation

A good score
needs a boundary.

IntentDesk evidence ↗

IntentDesk reports 96.24% known-intent accuracy on 4,500 requests. That result describes one benchmark. It does not establish that unfamiliar requests can be safely accepted.

The project records that its unsupported-input policy failed and remains disabled. Keeping that failure beside the stronger result makes the evaluation easier to interpret.

Questions to keep with a result

What task was tested? How was the model selected? Was the final test kept separate? Which inputs fall outside the benchmark? What happens when a prediction is wrong?

The La Liga project makes a related point: the richer workflow did not beat its frozen baseline. More architecture does not guarantee a better result. Read the recorded comparison.

Study note 03 · Traceable data

Keep the original
within reach.

QuoteCheck architecture ↗

QuoteCheck links extracted quotation information back to the original PDF or spreadsheet. The Kerala Crime Map separates official aggregates from news context and explains the population baseline used for rates.

These are different applications with a shared design concern: an interpretation should not erase the source.

Make uncertainty inspectable

A missing value should remain visibly missing. A partial-year total needs a reporting period. A model score should not silently turn into approval. These details help someone decide what a result can reasonably support.

Explore the idea step by step in the interactive pipeline, or read the Kerala Crime Map methodology summary.
